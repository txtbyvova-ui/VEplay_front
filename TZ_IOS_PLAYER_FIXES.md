# ТЗ: фиксы плеера по фидбэку полевого теста (iOS Safari / iPad)

Документ для Claude Code. Цель — вычистить 3 подтверждённых бага UX/воспроизведения
на iOS. ТЗ привязано к **реальному** коду репозитория `VEplayfront`, а не к общим
советам. Перед началом прочитай раздел «Архитектура: как есть на самом деле» —
часть популярных рекомендаций к нашему коду НЕ применима.

---

## Архитектура: как есть на самом деле (не игнорировать)

1. **`<audio>` создаются программно, не в JSX.** Два элемента (A и B) для
   кроссфейда создаются через `new Audio()` в `src/hooks/usePlayer.ts`
   (`make()`, строки ~123–130). Поэтому совет «добавь `playsInline={true}` в JSX
   тег» — **неприменим**. Атрибут надо ставить на объект: `el.playsInline = true`.

2. **Звук идёт через Web Audio graph.** `src/audio/graph.ts`:
   `<audio> → MediaElementSource → gain (кроссфейд) → compressor → master → destination`.
   Громкость на мобилках управляется master-`GainNode`, потому что iOS игнорирует
   `HTMLAudioElement.volume`. **Важно:** пока элемент подключён к `AudioContext`
   через `MediaElementSource`, его звук завязан на состояние контекста. iOS
   **усыпляет `AudioContext` (`suspended`) при блокировке экрана / уходе Safari в
   фон** → тишина, даже если сам `<audio>` мог бы играть в фоне. Это и есть
   главная причина «смерти в фоне», а не отсутствие `playsInline`.

3. **Ползунки — это НЕ `<input type="range">`.** Таймлайн и громкость — кастомные
   `<div>` в `src/components/PlayerScreen.tsx` (progress ~393–417, volume ~429–448)
   с обработчиками только `onTouchStart` + `onClick`. Обработчика движения
   (`move`) нет вообще → отсюда «работает только тап, тащить нельзя». Совет про
   `touch-action` на `<input type=range>` мимо — правим наши `div`.

4. **`viewport-fit=cover` уже стоит** в `index.html` — значит `env(safe-area-inset-*)`
   рабочие, надо только применить их в нужных местах.

5. **Play/Pause уже переписан** на привязку к нативным событиям (`togglePlay` в
   `usePlayer.ts` ~342–366, слушатели `play`/`playing`/`pause` на ОБОИХ элементах
   ~411–419). Регрессию «кнопка не пашет» из старой переписки, скорее всего, уже
   закрыли — этот пункт идёт как **верификация**, переписывать с нуля НЕ надо.

## BUG 1 — [CRITICAL] Музыка глохнет при блокировке экрана / сворачивании Safari

> **Статус: реализовано по рекомендованному варианту (фон > слайдер громкости).**
> На iOS/iPadOS элементы НЕ подключаются к Web Audio graph и играют напрямую в
> железо; `playsinline`/`webkit-playsinline` выставлены атрибутами; кроссфейд там
> вырождается в стык 0.4 с (гейнов нет, `el.volume` iOS игнорирует, а 6 с двух
> дорожек на полной громкости хуже стыка); при возврате из фона зовётся
> `graph.resume()` там, где graph есть. Слайдер громкости на iOS заменён подписью
> «Громкость — кнопками устройства», чтобы не показывать мёртвый контрол.
> Десктоп и Android остаются на graph — компрессор и программная громкость на
> месте. **Критерий приёмки (звук при погашенном экране iPad) проверяемым в этой
> среде не является — нужен реальный iPad.**

**Где:** `src/hooks/usePlayer.ts` (`make()` ~123–130), `src/audio/graph.ts`.

**Две причины:**

- **1a.** Программные `<audio>` не получают `playsInline`. В `make()` добавить:
  ```js
  el.playsInline = true
  el.setAttribute('playsinline', '')
  el.setAttribute('webkit-playsinline', '')
  ```
- **1b (корневая).** Весь звук маршрутизируется через `AudioContext`. При блокировке
  iOS переводит контекст в `suspended` → полная тишина. Одним `playsInline` это НЕ
  лечится.

**Требуется архитектурное решение (developer НЕ выбирает молча — см. «Открытый
вопрос» ниже).** Рекомендуемый вариант для B2B-сценария «iPad на барной стойке,
экран гаснет, музыка играет сама»:

- На iOS **не подключать** элементы к Web Audio graph: `<audio>` играет напрямую в
  железо (переживает блокировку и фон вместе с MediaSession).
- Кроссфейд на iOS делать через `el.volume`-рампы (fallback-ветка уже
  существует в `applyGain`, `usePlayer.ts` ~110–119) вместо gain-нод.
- Следствие-компромисс: на iOS внутренний слайдер громкости может стать
  неэффективным (iOS часто игнорирует `el.volume`), громкость регулируется
  аппаратными кнопками. Для заведения это приемлемо — фон важнее слайдера.
- На десктопе оставить текущий Web Audio graph (компрессор + громкость).

**Дополнительно (обязательно, независимо от варианта):**
- В `mediaSession.ts` состояние уже проставляется (`setPlaybackState`,
  `setPositionState`) — проверить, что вызывается при каждом play/pause/seek.
- Добавить обработчик `visibilitychange`: при возврате из фона —
  `graph.resume()` (уже есть функция), чтобы на десктопе/там где graph активен звук
  не оставался приглушённым.

**Критерий приёмки:** на реальном iPad — запускаем трек, гасим экран кнопкой /
сворачиваем Safari → звук продолжает играть, на локскрине видны название/исполнитель
и рабочие play/pause/next.

## BUG 2 — [UX] Ползунки не тащатся (таймлайн и громкость), только тап

> **Статус: закрыт.** Оба контрола переведены на Pointer Events с
> `setPointerCapture`, `touch-action: none` и локальным `scrub`/`volDrag` для
> визуала. Осталось подтвердить на реальном iPad.

**Где:** `src/components/PlayerScreen.tsx` — progress bar (~393–417), volume (~429–448).

**Причина:** только `onTouchStart`/`onClick`, нет обработчика движения; у контейнера
таймлайна нет `touch-action` → палец скроллит страницу вместо перемотки.

**Фикс (перевести оба контрола на Pointer Events):**
- `onPointerDown` → `e.currentTarget.setPointerCapture(e.pointerId)`, начать drag.
- `onPointerMove` (пока зажато) → обновлять **локальный** стейт «визуальной» доли
  (`scrubRatio`), чтобы заливка и «кнопка» ползунка ехали плавно под пальцем.
- `onPointerUp` / `onPointerCancel` → зафиксировать результат:
  - таймлайн: `seek(ratio)` (реальный `audio.currentTime` — только на отпускании,
    чтобы не дёргать элемент на каждый пиксель);
  - громкость: можно применять и вживую в move (дёшево, master-gain делает мягкую
    рампу), но локальный стейт всё равно ведёт визуал.
- На обоих контейнерах поставить `touchAction: 'none'` (сейчас у таймлайна его нет;
  у громкости стоит `manipulation` — заменить на `none`).
- Во время drag показывать `scrubRatio`; когда не тащим — реальный `progress`/`volume`.

**Критерий приёмки:** на iPad палец плавно тащит и таймлайн, и громкость; страница
при этом не скроллится; при отпускании трек перематывается в выбранную точку.

## BUG 3 — [UI] Вёрстка прилипла к краям, кнопки лезут на чёлку/Dynamic Island

> **Статус: закрыт.** `env(safe-area-inset-*)` применены к верхним кнопкам,
> `.player-left`, `.player-right` (в т.ч. в мобильной медиа-ветке); блок
> таймлайна/громкости получил горизонтальный отступ; правая колонка скроллится
> вертикально вместо клипания. Осталось подтвердить на реальном iPad.

**Где:** `src/components/PlayerScreen.tsx` (верхние кнопки ~336, `.player-right` ~361),
`src/index.css` (`.player-left`, `.player-right`).

**Фикс:**
- Верхние кнопки «Админка/Выйти» (сейчас `top: 14, right: 16` без safe-area):
  ```js
  top:  'calc(14px + env(safe-area-inset-top))',
  right:'calc(16px + env(safe-area-inset-right))',
  ```
- Ландшафт (дефолтная раскладка iPad — колонки в ряд): левая и правая панели
  упираются в боковые края, где в ландшафте живут вырез/скругления. Добавить:
  - `.player-left` — `padding-left: env(safe-area-inset-left)`;
  - `.player-right` — учесть `env(safe-area-inset-right)` в правом паддинге
    (сейчас `28px 36px calc(28px + env(safe-area-inset-bottom)) 32px`).
- Блок таймлайна/громкости — добавить комфортный горизонтальный отступ от краёв
  (запрос теста: «отступы от краёв там, где таймлайн»).
- Проверить кейс «формат меньше — не входит»: правая колонка `justify-content:
  space-between` + `overflow: hidden` → на низком экране контент клипается. Разрешить
  вертикальный скролл колонки на маленькой высоте или ужать фикс-размеры.

**Критерий приёмки:** на iPhone/iPad в ландшафте и портрете ни один контрол не
перекрывается системными элементами; у таймлайна видимые отступы от краёв.

## BUG 4 — [VERIFY] Play/Pause

> **Статус: регрессия воспроизвелась, закрыта точечно (привязка UI к нативным
> событиям не тронута).** Найдено два дефекта, оба НЕ на iOS:
>
> 1. `play()` на `<audio>` без `src` в Chromium не резолвится и не реджектится
>    (Safari — реджектит, поэтому полевой тест на iPad этого не видел). `warmUp()`
>    ждал именно такой промис на «холостом» элементе B → `togglePlay` висел
>    навсегда, кнопка Play не работала вообще. Приминг теперь получает 0.05 с
>    тишины (data: URI), плюс у `warmUp()` есть жёсткий дедлайн.
> 2. Отложенный `pause()` уходящего элемента в `switchTo` не проверял, не стал ли
>    этот элемент снова активным. Ручной next внутри 6-секундного окна
>    авто-кроссфейда → через 6 с глохнет уже играющий трек.

Код `togglePlay` уже привязан к нативным событиям элементов (правильный паттерн для
dual-player). **Не переписывать.** Только проверить на прод-сборке:
- пауза реально останавливает активный элемент;
- иконка Play/Pause всегда совпадает с реальным звуком, в т.ч. сразу после
  кроссфейда;
- локскрин-кнопки play/pause (MediaSession) дергают тот же `togglePlay`.

Если регрессия воспроизводится — чинить точечно в слушателях `play/pause`
(`usePlayer.ts` ~411–419), не ломая привязку UI к событиям.

## Открытый вопрос к Роме/продукту (нужно решение до BUG 1)

> **Решено: приоритет «фон > слайдер громкости».** Реализовано (см. статус BUG 1).
> Следствия, которые надо принять: на iOS нет компрессора (выравнивания громкости
> между треками) и нет программной громкости — только аппаратные кнопки; кроссфейд
> на iOS — стык, а не плавное перекрытие. Если решение изменится, откатывается
> одним флагом `bypassRecommended()` в `src/audio/graph.ts`.

Фоновое воспроизведение на iOS и внутренний слайдер громкости на iOS **конфликтуют**:
Web Audio даёт громкость, но глохнет в фоне; прямой `<audio>` играет в фоне, но
теряет программную громкость на iOS. Для «iPad на стойке» рекомендую приоритет
**фон > слайдер громкости** (громкость — аппаратными кнопками). Подтвердить.
